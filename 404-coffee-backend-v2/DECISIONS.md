# Implementation Decisions

## D-001 — مشروع مستقل

- الحالة: معتمد.
- القرار: إنشاء `404-coffee-backend-v2` من الصفر وعدم نسخ أو تعديل الباك القديم.
- السبب: المتطلبات تنص على MERN/Mongoose وتصميم جديد مستقل.

## D-002 — مرجع التنفيذ

- الحالة: معتمد.
- القرار: ملفات `backend-design/final-2` هي المرجع القانوني، وبالأولوية: ERD/Schema ثم API ثم Architecture ثم Canonical Blueprint ثم Codex execution plan.
- السبب: هذه الملفات تطبق آخر القرارات بلا ملاحق قديمة متعارضة.

## D-003 — Cash only

- الحالة: معتمد.
- القرار: `paymentMethod=CASH` فقط. `collectionMode=DIRECT` للطاولات والتيك أواي، و`COD` للتوصيل.
- الأثر: لا Payment Gateway ولا Card/Transfer ولا Payment Webhook.

## D-004 — MongoDB Transactions

- الحالة: معتمد.
- القرار: أي عملية تمس أكثر من Collection حرجة تستخدم MongoDB Transaction على Replica Set.
- الأثر البيئي: Mongo المحلي وDocker غير متاحين في Baseline؛ يجب توفير Replica Set في دفعة Scaffold/Integration قبل التحقق من المعاملات.

## D-005 — Frontend API migration

- الحالة: مؤجل لمرحلة الربط.
- القرار: العقد الجديد `/api/v1` هو المصدر الصحيح. لن نقلد المسارات القديمة بصورة عشوائية.
- السبب: تقليل الدين التقني ومنع وجود عقدين مختلفين دائمًا.
- التنفيذ اللاحق: تحديث `new desktop/src/services/endpoints.js` و`VITE_API_BASE_URL` مركزيًا بعد استقرار API، مع Adapter انتقالي فقط إذا أثبتت اختبارات الربط الحاجة.

## D-006 — Frontend AGENTS scope

- الحالة: مسجل.
- القرار: تعليمات `new desktop/AGENTS.md` تطبق عند تعديل الفرونت فقط: Mobile-first، touch targets 44px، RTL، وعدم overflow.

## D-007 — تغييرات Git السابقة

- الحالة: Baseline.
- القرار: الحذف والتعديلات الموجودة خارج v2 سابقة لهذه المرحلة. لا يتم Restore أو Commit أو تعديل لها ضمن تنفيذ الباك الجديد.

## D-008 — صلاحيات الدفع والفواتير

- الحالة: معتمد.
- القرار: صلاحيات الدفع `payments.read/collect/settle/refund` والفواتير `invoices.read/print` بنفس نمط صلاحيات الدرج، وتُربط كل route بصلاحيتها عبر `requirePermission`.
- السبب: الملف المرجعي يشترط صلاحية لكل Endpoint كتابة ولا يسمي المفاتيح حرفيًا؛ فاعتُمدت التسمية المتبعة في الكود الحالي.
- الأثر: أي route دفع/فاتورة جديد يلتزم بنفس البادئات.

## D-009 — اعتماد الدفع والفواتير على الطلبات

- الحالة: معتمد.
- القرار: موديولا الدفع والفواتير يقرآن الطلبات عبر typed `ordersPort` فقط (`getForPayment/applyPaymentSummary/getSummary/getInvoicePayload`)، وغيابه يفشل مغلقًا بـ503 `ORDERS_PORT_UNAVAILABLE` مع rollback كامل، والاختبارات تستخدم mock للمنفذ فقط ولا يوجد Mock في Production path.
- السبب: نفس نمط الدفعات السابقة (Drawer adapter المؤقت في الدفعة 5)؛ والدفعة 13 (الطلبات) هي التي ستوفر المنفذ الفعلي.
- الأثر: أي دفع/فاتورة حقيقية قبل الدفعة 13 يعيد 503 مقصودًا.

## D-010 — تخصيصات الطلبات على سجلات المخزون نفسها

- الحالة: معتمد.
- القرار: لا توجد Collection مرآة لتخصيصات الطلبات؛ الصنف يحفظ `allocationIds` والتفاصيل تُقرأ من `InventoryAllocation`، والاسترجاع عبر `restoreAllocations` نفسها.
- السبب: يمنع ازدواج المصدر وعدم تطابق المرآة مع الأصل عند الاسترجاع.
- الأثر: أي استعلام عن تكلفة صنف يجمع من `InventoryAllocation` بالـIDs المحفوظة.

## D-011 — الإلغاء يقترح الرد ولا ينفذه

- الحالة: معتمد.
- القرار: إلغاء الصنف أو الطلب يعيد المخزون ويعيد `refundCase` بمبلغ مقترح عند وجود مدفوع صافي، ولا يستدعي `createCashRefund` تلقائيًا؛ الكاشير ينفذ الرد عبر API الدفع.
- السبب: نفس فصل الخطوات المتبع في تسويات الموردين؛ الرد النقدي يحتاج درجًا مفتوحًا وقرارًا صريحًا.
- الأثر: `POST /orders/:id/cancel` لا يغير أي دفعة نقدية.

## D-012 — انتقال الجاهزية ضمن الطلبات وشاشاتها لاحقًا

- الحالة: معتمد.
- القرار: `POST /preparation/order-items/:itemId/ready` منفذ ضمن الدفعة 13 كشرط لاشتقاق READY والإتمام، وشاشات التحضير (current/ready/detail) مؤجلة للدفعة 14.
- السبب: Exit Criteria تطلب كل transition قبل الإغلاق.
- الأثر: لا توجد شاشة مطبخ بعد؛ الانتقال متاح عبر API فقط.

## D-013 — شاشات التحضير والوصفة المجمدة

- الحالة: معتمد.
- القرار: شاشات التحضير بصلاحية `preparation.read` المنفصلة عن `preparation.update`، وترتيب FIFO الأقدم أولًا، والقائمة بلا وصفة والتفاصيل بالوصفة المجمدة المخزنة على الصنف لحظة التأكيد.
- السبب: المطبخ يحتاج الوصفة للتحضير (صلاحية موظفين) بينما القائمة السريعة لا تحتاجها؛ والتجميد يمنع تأثر طلب قائم بتعديل وصفة لاحق.
- الأثر: أي تعديل وصفة يؤثر على الطلبات الجديدة فقط.

## D-014 — العملاء والتقييمات

- الحالة: معتمد.
- القرار: مفتاح العميل `phoneNormalized` بالتطبيع الحالي؛ الإلغاء لا يخصم `orderCount`؛ التقييم الإداري (تقديم/تعديل/إخفاء) بصلاحيات `reviews.*` المنفصلة، وتقييم العميل بالتوكن في الدفعة 16؛ تقييم `DINE_IN` مرفوض حاليًا لحين جلسة الطاولة في الدفعة 19.
- السبب: فصل مسار الإدارة عن مسار العميل العام، ومنع تقييمين بأي مالكين عبر فهرس `orderId` الفريد.
- الأثر: `socialLinks` مخزنة بلا تحقق خارجي؛ دمج هاتفين يدويًا غير مدعوم بعد.

## D-015 — سياسة الواجهة العامة

- الحالة: معتمد.
- القرار:
  - مدد التوكنات (غير موثقة في الملف): قراءة 30 يومًا، إجراء 7 أيام، جلسة عميل 30 يومًا.
  - هيدر جلسة العميل (غير مسمى في الملف): `X-Customer-Session`.
  - طلب الإلغاء العام (القاعدة غير موثقة): غير المدفوع في CONFIRMED/PREPARING يُقبل تلقائيًا ويُنفذ؛ غير ذلك PENDING للإدارة.
  - `deliveryConfirmation` في الاستلام null حتى الدفعة 17 التي تنشئ سجلات التأكيد.
  - حد البحث 10/10دقائق لكل IP وطلب بمنفذ ذاكرة داخل الموديول لحين محدد المعدل العام.
  - عقد التخزين المحلي: `{orderNumber, trackingReadToken, orderActionToken}` فقط ولا ثقة خادم به.
- السبب: سد فجوات التوثيق المسجلة في المراجعة بأقل افتراض آمن.
- الأثر: أي تغيير مدد أو حد يتطلب تحديث الثوابت المصدرة والاختبارات.

## D-016 — التوصيل والإسناد

- الحالة: معتمد.
- القرار: إسناد نشط واحد لكل طلب بفهرس جزئي؛ التسوية بعد التوصيل فقط وللمعلق من COD فقط؛ الواتساب تسجيل فتح رابط بلا ادعاء إرسال؛ إلغاء طلب مسند لا يغلق إسناده تلقائيًا (تسوية يدوية حتى آلة الحالات في مرحلة لاحقة)؛ استلام العميل العام يعيد استخدام `confirmDeliveryReceipt` نفسها فسجل التأكيد موحد.
- السبب: مطابقة الملف مع أقل افتراض، ومنع ازدواج مساري الإغلاق.
- الأثر: أي إغلاق تلقائي للإسناد عند الإلغاء يتطلب المرحلة 21.

## D-017 — الطاولات والجلسات

- الحالة: معتمد.
- القرار: مجموعة ثابتة 1-20 تُزرع كسولًا عند أول لوحة؛ الإشغال مشتق وليس مخزنًا؛ طلب الصالة DINE_IN بلقطة ضيف ثابتة وبلا upsert عملاء؛ إلغاء الجلسة يلغي طلبها؛ بيانات الطباعة لقطة قراءة فقط.
- السبب: مطابقة الملف مع أبسط حالة مخزنة، ومنع تلوث سجلات العملاء بضيوف الصالة.
- الأثر: جلسة الضيف العام (QR) ومقترحاته في الدفعة 19 فوق هذه الجلسات التشغيلية.

## D-018 — تجربة ضيف الطاولة

- الحالة: معتمد.
- القرار: تدوير QR يدوي إداري (بلا مجدول) يبطل الجلسات؛ جلسة الضيف 12 ساعة؛ مقترح نشط واحد لكل جلسة؛ التأكيد يلحق بالمفتوح أو يفتح؛ طلبات خدمة الجرسون للمقترحات في الدفعة 20.
- السبب: مطابقة الملف مع أقل حالة، وفصل إشعار الخدمة عن المقترح نفسه.
- الأثر: الطاولات المزروعة بلا سر QR حتى أول تدوير؛ المقترح لا ينشئ طلب خدمة بعد.

## D-019 — خدمات الطاولة

- الحالة: معتمد.
- القرار: مفتاح المالك SESSION بعد التشغيل وGUEST قبله؛ المكرر المفتوح يُعاد ولا يُنشأ؛ الحساب يحتاج طلبًا نشطًا ولا يحرك درجًا عند الحل؛ المياه/الحفلة بلا خصم مخزون؛ نداء المراجعة تلقائي مع المقترح ويُحل عند التأكيد؛ الإغلاق يحل الحساب ويلغي الباقي.
- السبب: مطابقة عقد الملف حرفيًا مع أقل حالة مخزنة.
- الأثر: لا إشعارات لحظية بعد؛ البث الحي في مرحلة Realtime.

## D-020 — حالات الإلغاء والاسترداد

- الحالة: معتمد.
- القرار: الموافقة الإدارية تنفذ الإلغاء فورًا (لا حالة وسيطة)؛ طلبات خارج التوصيل تُرد للمحل أولًا؛ إعادة المحاولة تبقي المعلق بلا استثناء عند العجز؛ المسح 50 طلبًا؛ إلغاء الطلب يغلق إسناده النشط بحالة CANCELLED الجديدة.
- السبب: خطوة واحدة حاسمة بدل حالات معلقة، وفصل الرد النقدي عن الإلغاء المخزني.
- الأثر: لا إشعارات تلقائية للعميل بنتيجة المراجعة بعد؛ القناة في مرحلة الإشعارات.

## D-021 — الداشبورد والمزامنة

- الحالة: معتمد.
- القرار: الداشبورد تجميع حي بسياسة قدم 60 ثانية بدل projector تدريجي؛ المزامنة من Outbox بحد 100 ولقطات للطلبات والجلسات؛ الغرف التشغيلية لكل موظف نشط والإدارية بالصلاحية؛ نقل Socket.IO الحي مؤجل والـ seam (المشتركون) جاهز؛ غرف الدرج مؤجلة لحين حمل حمولات الدرج لنطاقها.
- السبب: `Socket ليس مصدر الحقيقة` — المزامنة هي مسار التعافي الموثق، والنقل الحي طبقة توصيل لاحقة.
- الأثر: أي projector تدريجي لاحق يجب أن يحترم نفس المغلف والغرف.

## D-022 — التقارير والتدقيق

- الحالة: معتمد.
- القرار: التقارير قراءة فقط بكاش 5 دقائق؛ المصدر الفاشل null معلن؛ التصدير معالجة فورية مع 202 والحمولة مضمنة بحد 500 صف وبلا تخزين ملفات بعد؛ الإشعارات تُنشأ عبر منفذ فقط بلا مولدات تلقائية بعد.
- السبب: مطابقة العقد مع أقل بنية، وفصل التخزين الخارجي لمرحلة العمليات.
- الأثر: أي تصدير ضخم فوق 500 صف أو ملفات خارجية يتطلب مرحلة العمليات.

## D-023 — الباريستا الذكي

- الحالة: معتمد.
- القرار: أداة كتالوج وحيدة وإسقاط عام فقط؛ الرد غير القابل للتحليل يسقط للبديل المحلي؛ حد 20/دقيقة؛ إجراءات السلة خاملة؛ ربط الفرونت بلا تغيير شاشات.
- السبب: ضمان الكتالوج فقط على مستوى الخادم لا بثقة المزود، واستمرارية الخدمة بلا مفتاح.
- الأثر: مفتاح DeepSeek اختياري تشغيليًا؛ باقي مسارات الفرونت القديمة تنتظر هجرتها الخاصة.

## D-024 — بوابة الإطلاق

- الحالة: معتمد.
- القرار: الفهارس تُفحص ولا تُحذف تلقائيًا؛ الترحيلات فارغة والقفل إيجار قابل للانتهاء؛ الزرع idempotent والتسميات عربية لكل المفاتيح؛ الأدمن مرة واحدة بلا طباعة سر؛ المانيفست 187 مسارًا يجبر التحديث الواعي؛ المسارات بلا body تتحقق بجسم فارغ صارم.
- السبب: إغلاق الفجوات التي تمنع أول تثبيت حقيقي (كتالوج الصلاحيات والفهارس والإقلاع نفسه).
- الأثر: أي مسار جديد يكسر فحص العقود حتى تحديث المانيفست عمدًا.

## D-025 — الوسائط والنقل والعمال

- الحالة: معتمد.
- القرار: صور محلية بفحص بصمة (بلا AV خارجي بعد) وروابط موقعة ربع ساعة؛ السوكت بنفس مصادقة HTTP وغرف الطلب/الطاولة للموظفين فقط عبرها (العملاء على المزامنة)؛ العمال تيك محقونة من `server.js` فقط عند التفعيل.
- السبب: أقل بنية تشغل المسارات كاملة مع إبقاء الفحص الخارجي والحمل لمرحلة العمليات.
- الأثر: التخزين المحلي لا يصلح لأكثر من نسخة تشغيل واحدة؛ الكائنات الخارجية لاحقًا.

## D-026 — ربط الفرونت التدريجي

- الحالة: معتمد.
- القرار: طبقة services فقط بدوال v1 جديدة بجانب القديمة؛ الكتالوج مزدوج الشكل؛ التبني شاشة بشاشة لاحقًا؛ المسارات القديمة لا تُحذف حتى اكتمال الهجرة.
- السبب: منع كسر الشغال أثناء الانتقال، وكل دالة جديدة قابلة للتبني المستقل.
- الأثر: الشاشات ما زالت على العقد القديم ما عدا المحادثة.

## D-027 — التحقق الحي على Atlas

- الحالة: معتمد.
- القرار: قاعدة `cafe_erp` للبيانات المرجعية فقط؛ أي تجربة تكامل على قاعدة `cafe_erp_integration` المنفصلة وتُمسح بعدها؛ تاريخ حركة الاسترجاع افتراضيًا تاريخ اليوم عند غياب تاريخ العمل؛ `redactSensitive` تحفظ القيم غير العادية (تواريخ وBSON) كما هي ولا تعيد هيكلتها.
- السبب: أول تشغيل حقيقي كشف ما لا تكشفه الـ mocks (كتابة السكيما الفعلية).
- الأثر: بوابة `realReplicaSetIntegration` أصبحت verified بتاريخ التنفيذ.

## طريقة إضافة قرار

كل قرار جديد يأخذ رقمًا، وحالة، وسببًا، وأثرًا على Schema/API/اختبارات. لا يُستخدم الملف لاستبدال متطلب واضح دون تسجيل التعارض.

## D-028 - Admin role bypasses device approval

- Context: owner request; admin locked out by device-approval UX on every new device.
- Decision: in auth.service login(), an employee whose role name is 'Admin' (or level >= 100) gets new devices created APPROVED and existing PENDING devices upgraded to APPROVED, then login completes 200 with tokens.
- Scope: Admin role only. All other roles keep PENDING/BLOCKED flow, refresh still revokes non-approved sessions, audit attempts still recorded.
- Risk accepted: password-only trust for admin devices. Revisit with env flag if needed.
